## 2. 共用的组织方法

从三个样本可保留的一致方法是：先明确对象及其所有者，再维护派生文件、场景和验证记录。机械装配、仿真描述和业务任务分别管理，数据通过明确的接口契约连接。

| 责任 | 本项目可采用的组织方式 | 依据 |
|---|---|---|
| 机械权威模型 | 稳定的整星/子装配边界；零件、设备、紧固件和定位特征均有装配归属 | OreSat 的框架、卡件、背板和设备迭代 |
| 机器人描述 | 顶层组合、属性/惯量、分组件定义和仿真控制块分开；指定唯一权威模型，其余格式派生 | Space ROS demos 的 description、URDF/xacro 与 SDF 组织 |
| 场景和任务 | 世界、场景、规划、控制配置与任务流程分开；场景文件不承担结构参数真值职责 | Space ROS demos 的 sim/world、planning、demo/task |
| 求解器与可视化 | GJM/自由漂浮求解器和 ROS/可视化适配层分别版本化 | `ros_trick/` 等外部求解器桥接示例 |
| 工装与检查体 | 飞行件、装配/振动工装、规范 keepout 分开维护，再在顶层装配检查接口 | OreSat 的 AssemblyJig、VibrationJig、VolumeKeepout |
| 发布与追溯 | 文件名表达对象身份；版本、来源提交和派生关系进入发布记录，避免以重复复制文件表达版本 | OreSat 的 CAD/制造导出分层及贡献约定 |

原文中的 `sim_assets/description/`、`sim_assets/worlds/`、`sim_assets/scenes/` 是当时的职责示意，不是当前根目录建目录指令。现有八域下，机械权威及配置归 `20_engineering/`，仿真资产和场景归 `30_simulation/`，工具归 `70_tools/`，外部原件归 `80_third_party/`；具体子路径服从现有入口和所有权。

配置应区分控制器、关节限位、初始位形、运动学、可视化和求解器参数。规划限制引用本项目已冻结的关节与坐标契约；上游演示的同名字段不能自动成为本项目参数。

## 3. 装配、BOM 与质量代理

原文建议的装配责任可归并为下表。它描述对象关系，不指定新产品构型或新的物理数值。

| 装配对象 | 责任边界 |
|---|---|
| `BUS-TOP`、`BUS-PRIMARY` | 收拢整星顶层、主框/横框、部署器或适配器接口 |
| `BUS-SECONDARY` | 外板、舱板、设备托盘及其连接 |
| `B601-MOUNT`、`B601-HDRM` | 根部载荷扩散、定位、紧固、服务接口，以及发射锁和载荷旁路 |
| `PAYLOAD/EPS/ADCS/COMM/OBC` | 各子系统设备及其局部支架 |
| `HARNESS`、`COTS` | 路由、连接器、服务环、应力释放；采购件规格与来源 |
| `KEEP-OUT` | 部署器、太阳翼、B601、工具空间及适用规范的检查体 |
| `AIT-TOOLING` | 吊具、装配架、运输锁、振动夹具；不计入飞行 BOM |

OreSat 的历史说明了一条反复迭代的工作链：功能卡或载荷变化影响背板和接口，继而改变框架、孔位与定位；顶层检查暴露干涉和工具可达性问题，再同步更新紧固件、BOM、图纸及工装接口。应把热路径、维护、制造和装配可达性放入这条工作链。

BOM 可采用“固定项与随卡位/长度变化项分开”的分类；自制结构件、COTS 紧固件、部署件和卡级连接器分别计数。每个件号应能回到装配层级与图纸；卡级连接器可记录“卡数 × 单卡用量”的构成规则。原样本的 `framesBOM.xlsx` 只给出 1U/1.5U/2U/3U 的分档方法，不能直接外推 12U 件数。原文因缺少适用的 12U 架构与布局，将此类数值保留为 `PLACEHOLDER`；如以后外推，应记录 `ESTIMATED`、方法和不确定度。

质量代理采用独立记录：`geometry_mass_proxy` 与 `structural_material_property` 分栏，说明代理吸收了哪些未建模零件，并以实测称重回写偏差。等效密度用于质量闭合，不自动进入强度、刚度、热或模态计算。本项目 GJM、角动量预算和结构模型只读取各自准入的项目参数；演示机器人、OreSat 反作用轮 CAD 和代理密度不提供这些数值。

原文中 6061-T6、7075、表面处理和出气性能的待核事项，由迁移后的 [DOC_ACQUISITION.md](../../../20_engineering/system_design/legacy_root_structure/DOC_ACQUISITION.md) 保留；历史 [BOM_12U.yaml](../../../20_engineering/system_design/legacy_root_structure/BOM_12U.yaml) 与 [INTERFACE_ARM_BUS.yaml](../../../20_engineering/system_design/legacy_root_structure/INTERFACE_ARM_BUS.yaml) 同属旧结构合同，不因方法合并升级其数据权威。

## 5. 验证与复用限制

三个样本均提供组织方法，不替代本项目验证。Space ROS demos 原审计只确认了静态检查与逐演示容器构建；没有据此证明描述展开、动力学正确、启动烟测或端到端任务回归。其 Canadarm 示例通过固定世界关节约束基座，零重力设置不能作为自由漂浮耦合验证。URDF/xacro 与 SDF 并存，也未提供可继承的自动一致性证明。

本项目采用这些方法时，验证至少应分别覆盖：

1. 描述展开和语法，权威模型与派生格式一致性。
2. 控制器名称、关节集合、硬件接口及启动/时钟一致性。
3. 坐标、单位、质量和惯量的来源及合同。
4. 固定基座与自由漂浮场景的区别，以及本项目求解器所需的独立动力学验证。
5. 装配接触、退出路径、失败恢复、工具可达性和工装接口。

OreSat 的 `Frames/12U_Frames.SLDASM` 在原审计中仅是框架级原生装配，没有对应的 12U BOM 页、整星质量、质心或惯量文本证据。历史尺寸图的重量栏为空；keepout 和振动夹具也不提供当前 12U 部署器规范、发射谱、载荷、刚度或一阶模态要求。1U–3U BOM 趋势、历史材料库和 CAD 质量代理均不能填补这些缺口。

许可方面，原文要求按包及资产核对来源、许可证和署名条件：Space ROS demos 存在不同包许可证及未闭合项；SRB 父仓库许可证不覆盖全部第三方资产；OreSat 主库与 COTS 条款分开审查。原文列举的 CC0、Apache-2.0 或 CC BY-SA 资产仍需逐项记录各自条件，来源可见但许可不明的资产没有获准重新分发。该段保留历史审计要求，没有重新作出当前法律或资产许可判断。
