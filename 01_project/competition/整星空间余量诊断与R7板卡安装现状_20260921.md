# 整星空间余量诊断与 R7 板卡安装现状（2026-09-21）

本文回答两个问题：R6H 顶层装配收口后 AUX/STOP 装不进去，**是不是整星空间不足**；以及**要不要大改整星布局**。

所有结论以本轮机器裁决 JSON 为准，路径均在 `20_engineering/SERVICE_STAR_AUX_STOP_INSTALLATION_R7_20260921/results/`。本文不发布制造、上电或飞行许可。

---

## 1. 结论先行

**不是物理空间不足，是预留体积的分配问题。不建议大改整星布局。**

上舱 354 × 180 × 118 mm = **7.55 L**（`SHORTAGE_DIAGNOSIS.json`，2.5 mm 体素，占用由 AABB 保守外扩）：

| 类别 | 占上舱 |
|---|---|
| 实体硬件 | **40.7 %** |
| 预留体积 | 52.0 % |
| ——其中**独占**（该处根本没有任何硬件） | **33.1 %（2.50 L）** |
| 两者合计 | 73.8 % |
| 保留预留时的剩余空间 | 26.2 % |
| 解除预留后的剩余空间 | **59.3 %** |

独占预留的分布：

| 预留体积 | 占上舱 | 独占 | 独占体积 |
|---|---|---|---|
| `WP10_INTERNAL_BATTERY_BYPASS` | 33.3 % | 18.3 % | **1.40 L** |
| `WP10_RRC3570_4_D_MAX_ENVELOPE` | 20.0 % | 16.7 % | **1.28 L** |
| `PROP_PWR_ROUTE` | 7.4 % | 4.7 % | 0.36 L |
| `PROP_DATA_ROUTE` | 3.6 % | 2.7 % | 0.21 L |
| `equipment_adcs_propulsion_allocation` | 0.0 % | 0.0 % | 0 |
| `launch_interface_reserved_volume` | 0.0 % | 0.0 % | 0 |

**STOP 板需要 92 × 72 × 30.5 mm = 0.202 L，只相当于独占预留总量（约 3.25 L）的 6 %。**

硬件真实占用四成、且这还是包围盒放大后的数字；被四个不含任何硬件的信封挡住的体积是 STOP 需求的十六倍。这不是"整星塞满了"，是"体积都被信封先占了名分"。

## 2. 挡住 STOP 的具体是什么

两个大头都是**尚未与实物绑定的最大包络/旁路信封**，按命名就是待收紧的占位：

- `WP10_INTERNAL_BATTERY_BYPASS`：S 系 X −155…70、Y −85…6.5、Z −7…118，即 225 × 91.5 × 125 mm 的贯通块。
- `WP10_RRC3570_4_D_MAX_ENVELOPE`：X −54…135.5、Y −55.2…27、Z 7…92.5。名字里的 `MAX_ENVELOPE` 说明它是电池的**最大允许尺寸分配**，不是电池实物外形。

容量扫描（`BAY_CAPACITY.json`，2.5 mm 体素）两遍对照：

| 需要的层高 | 全部障碍下最大自由平面 | 仅硬件（解除预留）下最大自由平面 |
|---|---|---|
| 30.5 mm（STOP） | 120.0 × 47.5 mm | **220.0 × 80.0 mm** |
| 21.6 mm（AUX） | 120.0 × 62.5 mm | **227.5 × 92.5 mm** |

STOP 需要 92 × 72。保留预留时短 24.5 mm 装不下；解除预留后余量 2.4 倍。

## 3. 建议：不大改布局，收紧两个信封

按代价从低到高：

1. **把 `WP10_RRC3570_4_D_MAX_ENVELOPE` 收敛到 RRC3570-4 实物外形。** 这是"最大分配"降为"实际外形"，属于资料绑定而非设计变更，不动任何已装配件。
2. **把 `WP10_INTERNAL_BATTERY_BYPASS` 拆成实际线束走廊。** 现在它是一整块 225 × 91.5 × 125 mm 的贯通体，真实旁路线束不可能占满。R2 线束包已有走廊建模方法可复用。
3. 前两项之后重跑 `capacity.py` 与 `search_boards.py`，STOP 大概率直接落位。
4. 只有在 1、2 都做完仍装不下时，才谈布局大改。

**不建议现在动整星布局**：R6H 刚刚收口并通过逐实体复验，R4→R6H 这条链是目前唯一完整、可在 SolidWorks 打开的装配；为一块 0.2 L 的板去重排 7.55 L 的舱，代价与收益不成比例。

## 5. 本轮发现的方法缺陷（重要）

`BRepAlgoAPI_Common` 直接作用于**整块 PCBA 复合体**时会静默丢失真实干涉：

- 给 `R6H_MAIN_PCBA_INSTALLED` 打一根穿透销：整体 `0.000000 mm³`，逐实体 `70.400000 mm³`。
- AUX 板对双电池拉杆：整体 `0.0`，逐实体 `11.97 mm³`（板本体 11.31 + 一个元件 0.66）。

成因侧写：三块 PCBA 复合体自身存在自重叠实体（AUX 26 对 / STOP 100 对 / MAIN 28 对，合计 3.48 / 5.31 / 1.24 mm³），来源是板体被 Z 缩放到 1.6 mm 名义总厚而 KiCad 元件基准停在 1.595 mm；自相交的布尔操作数不是合法输入。合成用例（两只重叠方块的复合体）**不能**复现，因此这不是"复合体布尔普遍失效"的结论，只是这批操作数的性质。

**处置**：

1. R7 全部间隙判据改为逐实体（`tools/solid_wise.py`）。
2. R6H 用逐实体方法独立重验：`R6H_SOLIDWISE_RECHECK.json` = **`PASS_R6H_HORIZONTAL_CONFIRMED_PER_SOLID`**，129 对（其中 12 对涉及 MAIN PCBA）、0 碰撞、0 未知。**R6H 的 PASS 结论成立**，原方法偏弱但结果正确，现已有更强方法的独立确认。R6H 自身结果文件未被改写。
3. 用旧方法得到的 AUX 首个"干净"位姿（z=69）经复验实为碰撞，已归档为 `AUX_HORIZONTAL_SEARCH_ATTEMPT_01_REJECTED_WHOLE_COMPOUND_BOOLEAN.json`。
