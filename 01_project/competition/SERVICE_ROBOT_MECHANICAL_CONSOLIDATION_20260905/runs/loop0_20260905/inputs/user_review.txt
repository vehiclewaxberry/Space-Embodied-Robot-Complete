**可以进入下一轮，但下一轮应该是“针对已定位问题的受控整改”，而不是继续扩大总装、增加零件数量，或直接宣布机械设计已经闭合。**

这次WP03已经重新回到航天服务星本体：文件明确将主框、根部承载链、设备舱、完整B601、双三叶翼和两站随星保持器放进同一候选，地面装调装配另列。**不能再简单把它判成“只是机器人试验台”；但也不能把“整星画出来了”当成“整星机械系统成立了”。**

我的本轮总评是：

> **总体构成已经足以支持继续开发；连接、机构执行、完整运动验证和任务参数仍未闭合。最先需要修的，不是外形，而是验证依据、明确的局部结构缺陷，以及尚未实现的真实机构接口。**

# 二、对抗式审阅：现在最重要的六组问题

## 1. 已经存在明确的局部结构缺陷，不是只有“待补资料”

**上下设备甲板各有两处安装孔与立柱避让缺口连通。**

装配程序明确记录：X150、Y±89处的两个Ø3.4孔与X160处边口连通0.2 mm；上下两层都不能按八个完整安装孔计承载。

这应当成为**第一张实际改件任务**，因为问题位置、责任零件和关联接口已经足够清楚。

但不能只让Agent“把孔挪开一点”。应联合修改：

**设备甲板 → 绕柱角材 → 对偶紧固孔 → 螺钉头或垫圈承压区域 → 工具进入空间。**

通过条件也不能只是“布尔运算成功”。需要证明孔与缺口关系明确、对偶件同步、立柱仍可避让、紧固件可安装，并且没有产生新的设备或维护通道冲突。

**有意设计的开放槽可以成立，但必须按开放槽设计其定位、承载与防脱方式；把破边孔改名为“槽”，不算问题关闭。**

此外，根框到主梁、后端接口结构等连接也仍存在待落实事项。当前文件明确提醒：主框与根框需要真实锚固对偶，不能用接触或挂靠名称代替连接。

因此，“结构完整性”至少应分成：

> **零件有没有 → 对偶连接有没有 → 约束与载荷路径是否成立 → 给定载荷下是否满足要求。**

目前不能因为第一个问题大部分有答案，就认为后面三个已经成立。

---

## 2. 保持器已经有实体，但还不是完整的可执行机构

WP03的进步是真实的：保持器不再依赖蓝色地面高架，已经放到星体上。但文件仍明确列出导杆端部固定、销防脱、止挡、实际拉拔连接、驱动和退出后保持等缺口。

特别要审查下面这条链：

```text
星内电池/EPS
→ 释放驱动
→ 拔销及载荷卸除
→ 上下接触脱离
→ 保持器折退
→ 退出后保持
→ 状态确认
→ 机械臂首动许可
```

现在的26 mm退销、80 mm下鞋退让、100°开盖和90°折退，首先是**几何状态定义**。实际驱动连接、释放载荷、供电和确认接口仍未全部形成。

### 对图中侧伸保持架的审核意见

**不能凭它“看起来很长”就认定设计错误，也不能因为它被标为随星硬件就认为合理。**

下一轮应该量化它在退出后的代价：质量与偏心惯量、悬臂柔度、终位锁止、晃动或回弹空间，以及对臂、翼、相机和线束的影响。随后再判断是否需要更紧凑的折退方式。

同样，把下鞋退让从30 mm改到80 mm，解决的是已测试路径中的一个问题；**导杆加长后是否引入新的挠曲、卡滞或退出后约束问题，需要另验，不能随几何修正自动通过。**

这符合机构工程的基本工作范围：机构不仅需要几何表达，还需要设计、分析、验证及运行层面的证据。([欧洲航天标准化合作][2])

## 3. “179个实体通过、71个状态检查”不能合并成整星无碰撞

这是目前最容易在汇报中被放大的地方。

文件明确说明：

* 三态各179个非臂`PHYSICAL_GEOMETRY`有效、闭壳、正体积，静态成对检查没有检出正体积交叠；
* **该检查排除了完整机械臂、简化代理和功能空间**；
* 91个翼采样构型检查的是矩形叶片，不覆盖全部叉耳、销、线束、机械臂和样点之间的运动。

这些检查有价值，但不能互相拼成比原范围更大的结论。

### 还有两组候选没有收口

当前71状态记录仍保留：

**六种涉及功能包络的新配对，以及22种需要空腔精检的纯物理OBB候选。**其中B站导杆与释放盒约0.256 mm，是SAT最小轴重叠，不是已经确认的材料穿透深度。

正确处理应当是：

> 对真实材料配对做孔、轴、槽、空腔精检；对执行器功能包络，落实选型或受约束的尺寸方案。

不能因为OBB重叠就全部判实体碰撞；也不能因为是“功能包络”，就把它隐藏后判通过。

### 下一轮需要的不是更多截图，而是一张覆盖矩阵

每个结果至少绑定：

```text
部件对 × 几何表示 × 配置/路径 × 检查方法 × 容差 × 结果
```

允许接触应限定到具体部位和状态。**相邻link的安装面可以接触，不意味着整个相邻link配对都可以免查。**

完整臂源拓扑缺陷、accepted STL双指、完全包含以及连续运动，也都必须继续单独记录，不能被非臂主体检查覆盖。

## 4. 我在代码中发现了验证汇总的稳健性缺口

这部分不是重复文档中的待办，而是本次直接审阅代码得到的结果。

### 4.1 `pose_screen.py`是“限定历史候选筛查”，不是当前整星验收器

脚本直接从WP01读取参数和布局，并动态导入WP02的`motion_analysis.py`；固定根变换与指位也在脚本中定义。它自己明确写了`full_wp03_onboard_assembly_evaluated=False`。 

因此，它可以继续用于原本限定的筛查任务，但**不能因为文件放在WP03目录，就视为验证了当前WP03全部机构和硬件。**

需要增加机器可检查的对应关系：

> 当前WP03参数、实例集合、臂源、姿态与检查收据，究竟是不是同一组输入？

### 4.2 历史两姿态的标签需要更严格的继承条件

代码读取旧布局记录后，直接设置`SOURCE_REFERENCE_35_BODY_PAIRS_SURFACE_DISJOINT_FINGER_UNKNOWN`标签；在这一段可见代码中，没有先按旧结果内容、逐link来源哈希及姿态条件完成等价性检查，再决定是否设置该标签。

这**不证明历史结果是错的**，但说明其复用需要增加防护。

共同刚体变换不改变机械臂内部自交关系，但会改变机械臂与星体的关系；这两种继承范围也不能混用。

### 4.3 “检查了35条记录”不等于“检查了正确的35对”

目前状态分支主要根据有无相交记录，以及`checked == 35`选择标签。配对身份集合和`worker_completed`不参与这个分支的通过条件。

我从源码中隔离提取了这个表达式，用合成记录进行了测试：

| 合成输入               | 当前表达式的结果    |
| ------------------ | ----------- |
| 35对不同记录、均无表面相交     | 返回35对表面分离标签 |
| **34对不同记录＋1条重复记录** | **仍返回相同标签** |
| **35条非预期配对ID**     | **仍返回相同标签** |
| 35条记录但没有完成事件       | 仍返回相同标签     |
| 只有34条记录            | 返回不完整       |
| 存在一条相交记录           | 返回相交拒绝      |

**这个试验证明的是汇总逻辑缺少配对身份与完成状态防护，不是证明原CAD已经漏检。**

修复方向应是检查：

```text
实际唯一配对集合 = 预期配对集合
没有重复、缺失或额外配对
输入配置与哈希一致
运行结束状态及错误状态有效
每项方法和结果范围明确
```

此外，脚本当前会覆盖固定名称的结果文件。进入多Agent迭代前，应改为独立运行目录和输入快照，避免一个Agent读取结果时，另一个Agent正在改写它。

## 5. 研究模型可以继续，但不能继承旧构型的科学结论

目前WP03资料足以支持搭建**新的、带缺项说明的自由漂浮多体基线**，但不足以判断整个项目的控制、抓捕或具身闭环已经完成。

你自己的README已明确：整体惯量只对应锁定相对运动的指定构型；机械臂运动时应保留逐link自由度与基座耦合；新几何不能直接继承旧仿真的PASS。

尤其需要审查两个实质差异。

**质量口径：**20.716839 kg是已分配小计，不是实测完整质量；`mass_kg`与`allocated_dynamics_mass_kg`不能相加，也不能直接与旧31 kg系统模型比较后宣称减重。

**执行器能力：**来源记录指出，旧研究中的0.300 N·m·s轮组档与F4R1的4×30 mN·m·s候选不同，不能继承旧姿控或消旋能力。

所以，下一轮研究应先做**模型一致性、守恒检查和参数敏感性**，再做性能比较。未知设备质量、实际驱动能力和接触参数不能为了让仿真运行而默认为零或随便补值。

## 6. 文件混乱已经影响可复现性，但不能立即“删除旧版本”

这里有一条代码级的硬证据：

```python
WP01 = HERE.parent / 'service_robot_wp01_20260905'
WP02 = HERE.parent / 'service_robot_wp02_20260905'
# 随后读取WP01参数/布局，并加载WP02的motion_analysis.py
```

因此，**WP01和WP02目前至少部分仍是WP03的活动依赖，不是天然可归档或删除的旧文件夹。**

此外，README已经明确：若干继承参数并不驱动当前几何，部分孔系和厚度仍直接定义在主体生成器中。

这意味着当前混乱至少包括两种：

> **目录层面不知道该看哪个文件；参数层面不知道改哪个字段才真正改变模型。**

只做文件夹重命名，解决不了第二个问题，还可能破坏第一类活动依赖。

# 三、下一轮的闭合目标：不是“全部完成”，而是把六条链逐步接上

我建议采用下面这张闭合矩阵，不再使用一个笼统的机械完成度百分比。

| 闭合链        | 当前判断           | 下一轮必须补上的证据              |
| ---------- | -------------- | ----------------------- |
| **产品构成链**  | 已有完整随星候选表达     | 实件、代理、功能空间、GSE和缺失项逐实例对应 |
| **装配连接链**  | 部分已设计，局部明确有缺口  | 对偶面、孔轴、紧固、约束、工具与拆装路径    |
| **保持释放链**  | 几何候选已形成，执行链未完整 | 驱动、载荷卸除、导向、防脱、终位与状态确认   |
| **几何运动链**  | 有限定静态与采样证据     | 完整对象、正确配对、正常接触和样点间范围    |
| **力学及系统链** | 可做分析，输入尚不完整    | 真实边界、质量惯量、载荷、姿控、能源与热接口  |
| **数字证据链**  | 有大量记录，仍需绑定与防护  | 同源快照、独立检查、负控、依赖与可重建性    |

**允许在某些链未闭合时继续其他链的设计，但必须明确不能外推的结论。**例如，没有发射载荷不妨碍修复甲板破边孔；没有真实线缆不妨碍设计可调线夹，但不能据此宣称线束全程合格。

# 四、多Agent方案：七个逻辑角色，最多两个轻任务并行

你现在需要的是**独立的证据审查与单一CAD写入者**，而不是再开一批同时修改总装的Agent。

“协调者—工作者”和“生成—评价—改进”是已有的Agent组织方式；但使用它们的前提是评价标准明确，并能从工具结果取得反馈，而不是只互相评价文字。([Anthropic][3])

## 推荐分工

| 角色              | 主要职责                | 必须提出的对抗问题                |
| --------------- | ------------------- | ------------------------ |
| **A0 总协调**      | 配置锁定、任务分配、问题排序、停止条件 | “这个结论对哪一配置、哪一用途有效？”      |
| **A1 构型与文件审阅**  | 权威、哈希、依赖、整理风险       | “删掉或移动这个文件，会破坏哪个消费者？”    |
| **A2 结构审阅**     | 甲板、根框、连接、承载与可装性     | “接触处真的有连接，还是只是看起来贴住？”    |
| **A3 机构审阅**     | 保持器、臂翼、线束、驱动及故障状态   | “哪个中间状态或单点故障会使动作失效？”     |
| **A4 验证器审阅**    | 代码、覆盖、负控、独立复验       | “给它缺失、重复、错源或超时输入，会不会误报？” |
| **A5 系统与动力学审阅** | 质量惯量、姿控、能源、任务与旧结果迁移 | “换了几何和执行器后，旧结论还成立吗？”     |
| **A6 CAD构建者**   | 唯一几何与参数写入者          | “能否只改最少零件解决已复现问题？”       |

建议Codex承担协调和受控改件，Claude承担独立审阅；具体按本地可用工具和额度分配。**逻辑角色可以串行执行，不需要同时常驻七个进程。**

运行规则建议为：

**最多两个轻量读取任务并行；CAD构建、inspect和重型布尔检查最多一个；作者不验收自己的修改。**

各角色共用同一输入快照，但先独立形成结论，再交换意见。结论统一写到共享问题账本，不让每个Agent再创建一套“当前状态”“最终报告”和“权威入口”。

Agent意见不一致时，必须回到原始输入或复验。**多数票不能决定实体是否干涉，也不能决定机构是否能释放。**

# 五、Loop engineering：把反馈闭环落到真实问题上

适合你的闭环不是“让Agent一直做，直到说完成”，而是：

```text
锁定一个问题
→ 找到最小反例
→ 冻结接受判据
→ 修改最小范围
→ 独立复验
→ 相关回归
→ 接受或退回
```

近期关于loop engineering的工程实践，也将执行循环与验证循环分开，并强调人工监督的必要性。这里可以借用方法，不需要为了采用它再安装一套大型框架。([LangChain][4])

## 建议的下一轮任务序列

| 循环                | 具体工作                          | 完成标志                     |
| ----------------- | ----------------------------- | ------------------------ |
| **Loop 0：证据绑定**   | 核对当前原始收据、补验证器负控、建立依赖导航        | 每项结果对应同一配置；错误或不完整证据不会被接受 |
| **Loop 1：局部结构改件** | 修复甲板孔—避让口—角材—紧固关系，核查根框连接      | 问题消失、对偶一致、没有新增相关冲突       |
| **Loop 2：保持器执行链** | 落实导向、防脱、驱动与退出后保持，处理六类与22类候选配对 | 每对有证据，每个运动件有真实安装和动作依据    |
| **Loop 3：整星动作链**  | 同配置检查臂、保持器、翼、线束和确认条件          | 覆盖范围完整；采样结论与连续保证分开       |
| **Loop 4：研究模型交接** | 更新逐link惯性、随星质量及系统接口           | 新模型输入明确，旧结论不被无条件迁移       |
| **Loop 5：冷重建与整理** | 验证离开当前缓存/运行环境后仍能重建            | 活动依赖明确，再判断真正可退役的派生文件     |

### 每轮必须防止的“伪收敛”

不能通过删掉难检查的部件、放宽容差、减少配对、把物理件改成代理、把失败改名为“不适用”，来使指标变绿。

接受修改至少要求：

> 原反例消失，必需检查范围未缩小，负控仍能被拒绝，没有新增相关阻断，输入输出处于同一配置。

建议每张问题票最多三次尝试；连续两次没有改进，就定位原因或请求缺失输入。**这是计算与协作预算，不是工程合格标准。**

额度不足、权限失败或超时应停止对应分支并保留状态，不能反复拉起更多Agent，也不能把未完成任务写成通过。

# 六、项目整理：先得到“一套清楚的活动方案”，再减少物理文件

## 1. 不再新建另一套平行项目根目录

你已有的`PROJECT_MAP.md`规定了八个业务域，包括`01_project`、`20_engineering`、`30_simulation`、`40_evidence`等，并禁止新增平行业务根目录。整理应沿着这个结构推进，先核对本地是否有后续正式修订。

**不要再复制出一个“WP03_FINAL_CLEAN_NEW”大目录。**那通常只会新增一份来源难辨的工作区。

第一轮建议保持WP01/WP02/WP03原路径不动，建立以下逻辑关系：

```text
现有项目入口
├─ 当前服务星候选：指向WP03及确切修订
├─ 当前源码/有效参数/环境：明确真正驱动模型的文件
├─ 当前验证与已知失败：指向同源原始收据
├─ 下一张问题票：只给一个明确的最小任务
└─ 上游依赖：WP01、WP02、R2、accepted模型、厂家来源
```

NASA的构型管理方法强调对产品配置、变更及其状态进行识别和控制；**项目整洁首先是知道哪个版本有效、为何有效，而不是文件数量越少越好。**([NASA][5])

## 2. 文件至少分成这些角色

| 分类             | 处理原则               |
| -------------- | ------------------ |
| **活动源和必需上游**   | 保留当前位置，先解析依赖       |
| **冻结证据、历史负结果** | 保留，不因新版本存在而删除      |
| **厂家与第三方来源**   | 保留版本、许可及来源绑定       |
| **生成交付物**      | 区分当前交付、历史交付与可重建缓存  |
| **GSE分支**      | 与随星主入口分开，但不是自动删除对象 |
| **同字节重复候选**    | 先查引用、职责和备份，再决定是否隔离 |
| **无法判断的文件**    | 标记待确认，不强行归类为冗余     |

尤其要保留旧30 mm路径的真实碰撞反例。它是新验证器的回归输入，不是“失败所以没用”的垃圾。

## 3. 物理去重必须晚于依赖分析

相同SHA-256只证明文件内容相同，**不证明两个路径的作用相同，也不证明删掉一份不会断引用。**

后续清理候选必须附有：

```text
源文件及保留副本
→ 字节身份
→ 角色
→ 所有已知消费者
→ 未解析依赖
→ 迁移或替代映射
→ 冷重建结果
→ 回滚与批准记录
```

当前`pose_screen.py`还依赖旧目录，所以**不能先删除WP01/WP02，再指望Agent修好路径。**

也不要直接移动`results/`、批量替换相对路径，或清理嵌套Git、LFS与worktree。真正需要迁移时，应先在派生候选中解除依赖并验证。

**第一轮整理成果应是一个清晰入口和可解释的依赖图，不是一次大规模删除。**

## 最终裁决

**WP03值得继续，而且现在已有足够具体的问题可以进入下一轮开发。**但开发顺序应从“不断扩大模型”改成“用独立证据关闭真实缺口”。

我建议你立刻推进的组合是：

> **先完成一次有界的同源证据与依赖核查；随后优先修复设备甲板及对偶连接，同时把随星保持器从几何动作深化为真实机构。文件整理先做唯一入口，不做破坏性搬迁。**

下一轮的成功标志不再是多了多少STEP或报告，而是：**一个已复现的问题被真正解决、对应接口和验证没有退化，而且任何接手者都能找到唯一的当前方案并重现这个结果。**
